# Configuration reference

Every environment variable the platform reads, and every settings block in
`config/settings.py`, with its purpose, default, allowed values, warnings and
production notes. Variables are set in `metanoia/.env` (start from
`.env.example`), in the hosting platform's dashboard, or — for secrets on the
AWS host — in AWS Secrets Manager (see [deployment.md](deployment.md)).

## 1. How settings are read

* Copy the template: `cp .env.example .env`. `.env.example` is the file that
  belongs in version control and must never contain a real secret. For a new
  organisation, `.env` plus `.strings.json` (branding: name, logo, colours,
  contact details) should be all that needs changing.
* `config/settings.py` loads `BASE_DIR/.env` with `python-dotenv`. A missing
  `.env` raises a warning at import (`No .env file found …`); it is the most
  common cause of a cryptic `fe_sendauth: no password supplied` deep inside a
  management command, which is why the database password guard (section 5)
  names it.
* `load_dotenv` never overwrites a variable that already exists, so anything the
  host sets (platform dashboard, systemd `EnvironmentFile=`) wins over `.env`.
  `PROCESS_ENV` is a snapshot of the environment taken *before* `.env` is
  loaded; it is what lets the settings tell "the platform said so" from "the
  committed `.env` said so" after the merge.
* `platform_decides(name)` is true on a hosting platform when the platform did
  **not** set `name`. The repository's `.env` is tracked and travels with the
  code carrying development values (`DEBUG=True`, `ALLOWED_HOSTS=*`, a localhost
  database), so for `SESSION_COOKIE_SECURE` and `SITE_URL` the platform's
  knowledge wins over those values; `DEBUG` follows the same rule directly.
* Parsing helpers: `env_bool` accepts `1`, `true`, `yes`, `on` (any case);
  `env_int` falls back to the default when unset, blank or not a number;
  `env_list` splits on commas and drops blanks; `env_or` treats a declared but
  **blank** variable as unset (a blank `FILES_URL=` once stripped `/media/` off
  every file URL and rooted uploads at the project directory).
* On the AWS host the secrets listed in `deploy/server/aws/secret-keys.txt` are
  not in `.env` at all: they come from Secrets Manager through
  `/run/metanoia/secrets.env`, which systemd loads before Django starts. Use
  `deploy/server/aws/manage.sh` to run `manage.py` by hand with them loaded.
* `.env.example` declares `CSRF_TRUSTED_ORIGINS` twice (with the core
  variables, and again, empty, with the HTTPS variables). python-dotenv keeps the
  **last** assignment, so set the value you want in one place and delete the
  other in your `.env`.

## 2. Core

Always set these before any non-local deployment.

| Variable | Default | Notes |
|---|---|---|
| `SECRET_KEY` | none (development key only with `DEBUG` on or under tests) | Signs sessions, password-reset links and every JWT (`SIMPLE_JWT['SIGNING_KEY']`), so a short value weakens API auth as well as sessions — use the full 50 characters. Generate with `python -c "from django.core.management.utils import get_random_secret_key as k; print(k())"`. With `DEBUG` off and no key the process refuses to start (`ImproperlyConfigured`), because the fallback key is published in `config/settings.py` and anyone with the source could forge all three. `deploy.E007` (`apps.diagnostics.deploy_checks`) also catches a key *set* to the development value. On Render it is generated by the blueprint; on AWS it comes from Secrets Manager. |
| `DEBUG` | `True` locally; `False` on a hosting platform unless the platform itself sets it | **Never `True` in production**: it serves tracebacks, settings and source to the public, and looks as if it is working fine. The committed `.env` carries `DEBUG=True`, which is why a platform must set it explicitly to turn it on. |
| `ALLOWED_HOSTS` | `*` while `DEBUG` is on, otherwise empty | Comma-separated host names, no port (Django strips the port before matching). `*` accepts any `Host` header and defeats the protection against cache poisoning and password-reset links minted for an attacker's domain; never use it in production. `deploy.E001` / `deploy.E002` refuse to boot without real hosts. On Render the platform hostname is appended automatically and `*` is dropped. |
| `SITE_URL` | `http://127.0.0.1:8000`; on a platform, `https://<RENDER_EXTERNAL_HOSTNAME>` unless set | Absolute public base URL used for every link in e-mails: verification, password reset, invoice pay-links. Wrong does not fail loudly — users get links to somebody else's domain. Set it explicitly for a custom domain. |
| `CSRF_TRUSTED_ORIGINS` | empty | Comma-separated, scheme required (`https://example.com`). See section 9. |

`TESTING` (not an environment variable) is true under `manage.py test` or
pytest. The test runner forces `DEBUG=False`, so production-only guards (for
example `apps.finance.checks` refusing the PayFast sandbox) consult `TESTING`
to stand down during the suite.

## 3. Hosting-platform detection

Read from the platform's own environment (never from `.env`):

| Variable | Effect |
|---|---|
| `RENDER` | Sets `ON_RENDER`. |
| `RENDER_EXTERNAL_HOSTNAME` | Public hostname. Scheme, path and port are stripped for `ALLOWED_HOSTS` (an entry with a port can never match and every request would be 400 `DisallowedHost`); the port is kept in `RENDER_EXTERNAL_NETLOC` for CSRF origins and absolute links. |
| `RAILWAY_ENVIRONMENT`, `RAILWAY_ENVIRONMENT_NAME`, `RAILWAY_PROJECT_ID`, `RAILWAY_SERVICE_ID` | Any one sets `ON_RAILWAY`. |

On a platform (`ON_PLATFORM`) the defaults flip to production values with no
configuration: `DEBUG` off, the public host trusted, TLS assumed terminated
upstream (`USE_X_FORWARDED_PROTO` defaults on), `PAYMENTS_ENABLED` off, and the
LAN probe skipped.

## 4. Applications and middleware

Not environment-driven, but order matters.

**`INSTALLED_APPS`**

* `daphne` must be listed **first** so its ASGI-aware `runserver` replaces
  Django's WSGI one; `channels` provides consumers and routing (see
  `config/asgi.py` and `docs/WEBSOCKETS.md`).
* Project apps: `apps.accounts`; `apps.myhub` (dashboard pages); `apps.communication`
  (chat, meetings, notifications, announcements, e-mail); `apps.mailbox` (Metanoia
  Mail, Outlook-style IMAP/SMTP for staff and educators); `apps.msteams` (Teams
  live classroom via Graph); `apps.livesessions` (calendar, audience, reminders,
  recording pipeline); `apps.ai_assistant` (Claude helpers, `AiReport`/`AiInsight`);
  `apps.shop` (store, orders, payments, expiry); `apps.finance` (invoices,
  receipts, due payments); `apps.tasks` (**retired** — migrations only, drops the
  task tables; remove next release).
* My Learning Hub: `apps.learning` (modules, lessons, study timers),
  `apps.assessments`, `apps.reports` (weighted grades, report cards,
  certificates), `apps.analytics` (academic intelligence, risk monitoring),
  `apps.scheduler` (background jobs, `apps/scheduler/jobs.py`),
  `apps.diagnostics` (error dictionary and log), `apps.staffdesk` (`/staff/`),
  `apps.revision` (spaced-repetition cards from the student's own mistakes).
* `allauth.mfa` was chosen over django-otp because it plugs into the allauth
  login, signup, social-login and password-reset flows already in use instead of
  a second parallel login pipeline (see `docs/PACKAGE_DECISIONS.md`).
* `captcha` is the self-hosted math CAPTCHA (section 22); `axes` adds per-account
  and per-IP lockout with an auditable `AccessAttempt` / `AccessLog` trail on top
  of allauth's form throttling, which blocks but records nothing;
  `import_export` provides Excel/CSV import and export in the admin.

**`MIDDLEWARE`** (top to bottom)

* `ErrorCaptureMiddleware` is first so its `process_exception` runs last and
  sees exceptions inner middleware did not turn into a response.
* `TrafficMiddleware` times and counts requests for the System monitor;
  `UploadRedirectMiddleware` returns an upload's redirect as JSON for progress
  bars.
* `WhiteNoiseMiddleware` must sit directly after `SecurityMiddleware`. It serves
  `STATIC_ROOT` from the app process; with `DEBUG=False` Django does not serve
  static files and Render's free tier has no web server in front, so without it
  the site loads with no CSS, JS or images.
* `MediaSecurityHeadersMiddleware` is early so it stamps every `/media/`
  response, stopping an uploaded `.svg`/`.html` executing in the site's origin.
* `CounterInvalidationMiddleware` clears the user's cached navbar counters after
  any write.
* `UserPreferenceMiddleware` applies the saved theme and language (after auth,
  before rendering); `RuntimeTranslationMiddleware` translates un-marked HTML.
* `StudentViewMiddleware` (super student preview) runs before the access gates
  so they all judge the preview student.
* Access gates: login required site-wide, onboarding, management (admin/staff
  only), parent, community, module (content closes when a trial lapses unpaid),
  MFA required for privileged roles (opt-in).
* `SocialAppGuardMiddleware` turns allauth's crash on an unconfigured social
  provider into a redirect with an explanation.
* `AxesMiddleware` must be **last**: it needs the fully resolved request to
  attribute a failed login to the right account and IP.

**Templates**: all project templates live in `templates/<app>/`; `APP_DIRS`
stays `True` so allauth, DRF, guardian and the admin can use their bundled
templates. Context processors add branding (`.strings.json`), theme and
language, role flags, the student-view toggle, dashboard data, account stats,
the one-time updated-terms prompt, unread message and mail counts, shop and
finance totals.

## 5. Database

PostgreSQL is the only active database (`default`). All reads and writes go to
it through `core.db_router.PrimaryReplicaRouter`.

**Precedence.** A connection URL wins outright for name, user, password, host
and port; the `POSTGRES_*` variables are then ignored, not merged — half
overriding a URL with a stale `POSTGRES_HOST` is how a deploy quietly writes to
the wrong database, and the committed `.env` supplies `POSTGRES_*` everywhere.

* **Deployed** (Render, Railway, Heroku, Fly, Neon, Supabase): the platform
  injects `DATABASE_URL`. Nothing to set.
* **From a laptop against the hosted database**: `DATABASE_PUBLIC_URL`. The
  injected `DATABASE_URL` is a private address (Render's internal hostname,
  Railway's `*.railway.internal`) that does not resolve elsewhere. Off-platform
  the public URL is preferred; on-platform `DATABASE_URL` is. A
  `*.railway.internal` URL is skipped off-platform whichever variable holds it.
  Render: database page → External Database URL. Railway: Postgres service →
  Variables → `DATABASE_PUBLIC_URL`.
* **Neither set**: the discrete `POSTGRES_*` values (plain local Postgres).

| Variable | Default | Notes |
|---|---|---|
| `DATABASE_URL` | empty | `postgresql://user:password@host:5432/dbname?sslmode=require`. Only PostgreSQL schemes are accepted (`postgres`, `postgresql`, `pgsql`, with `+psycopg2`/`+psycopg`); anything else, or a URL with no host, raises `ImproperlyConfigured`. Credentials and name are percent-decoded (a password containing `@`, `/` or `:` arrives escaped). Query options kept: `sslmode`, `sslrootcert`, `sslcert`, `sslkey`, `options`, `connect_timeout`, `application_name`, `target_session_attrs`. |
| `DATABASE_PUBLIC_URL` | empty | As above; see precedence. |
| `POSTGRES_DB` | `metanoia_db` | |
| `POSTGRES_USER` | `postgres` | |
| `POSTGRES_PASSWORD` | empty | Required (secret). |
| `POSTGRES_HOST` | `127.0.0.1` | |
| `POSTGRES_PORT` | `5432` | |
| `POSTGRES_SSLMODE` | `require` for any remote host; unset for localhost, a unix socket and `*.railway.internal` | Overrides either way: `disable`, `require`, `verify-ca`, `verify-full`. A database reached over a network must be encrypted. |
| `POSTGRES_CONNECT_TIMEOUT` | `10` (seconds) | Without it an unreachable host hangs requests, `migrate` and the release command for minutes. |
| `POSTGRES_CONN_MAX_AGE` | `0` | **Keep 0 under ASGI.** Every sync view runs in a thread-pool thread with its own connection that Django never closes, so a value above 0 leaks connections until Postgres runs out of slots (the 2026-10-20 outage). Only raise it under WSGI against a remote database, where the TCP+TLS handshake costs 50–150 ms. |
| `POSTGRES_CONN_HEALTH_CHECKS` | `true` | Reconnects a pooled connection the server has closed instead of handing a dead socket to a view. |
| `POSTGRES_DISABLE_SERVER_SIDE_CURSORS` | `true` | Server-side cursors (`.iterator()`) live on one connection outside any transaction; if it is closed or recycled mid-loop the next fetch fails with `cursor _django_curs_… does not exist` (the re-engagement and reminder jobs did, 14 and 17 Oct). Client-side fetching is fine for this platform's result sizes. |

**Guards at import time**

* A `*.railway.internal` host off Railway warns that it will fail with "could not
  translate host name" and points at `DATABASE_PUBLIC_URL`.
* On a platform with no URL and a local host, startup fails: the container's own
  loopback has nothing listening; attach a managed database and expose
  `DATABASE_URL`.
* No password fails fast with a hint (URL without `:password@`, missing `.env`,
  or blank `POSTGRES_PASSWORD`) instead of psycopg2's `fe_sendauth: no password
  supplied` from inside a migration or a destructive command.

**Optional MySQL disaster-recovery copy.** The `backup` alias is not defined. To
add one, put this entry in `DATABASES`, set the `MYSQL_*` variables and install
a driver (see [dependencies.md](dependencies.md)); then keep its schema in step
with `python manage.py migrate --database=backup`. `settings.py` already falls
back to PyMySQL through `pymysql.install_as_MySQLdb()` when `mysqlclient` is
absent. `.academic_seed.py --fresh` wipes and migrates every alias in
`DATABASES`, so enabling it means a fresh seed touches MySQL too.

```python
'backup': {
    'ENGINE': 'django.db.backends.mysql',
    'NAME': os.getenv('MYSQL_DB', os.getenv('DB_NAME', 'metanoia_db')),
    'USER': os.getenv('MYSQL_USER', os.getenv('DB_USER', 'root')),
    'PASSWORD': os.getenv('MYSQL_PASSWORD', os.getenv('DB_PASSWORD', '')),
    'HOST': os.getenv('MYSQL_HOST', os.getenv('DB_HOST', '127.0.0.1')),
    'PORT': os.getenv('MYSQL_PORT', os.getenv('DB_PORT', '3306')),
    'OPTIONS': {'charset': 'utf8mb4'},
},
```

The default `User` model is used with the `apps.accounts.Person` profile;
`AUTH_USER_MODEL` is not overridden. `DEFAULT_AUTO_FIELD` is `BigAutoField`.

## 6. E-mail / SMTP

All branded e-mails (notifications, announcements, allauth auth e-mails) are
rendered through `apps.communication.emails` and
`templates/communication/email/`.

> **Warnings**
> * Port 587 requires `EMAIL_USE_TLS=true` (STARTTLS); port 465 requires
>   `EMAIL_USE_SSL=true`. Never set both. With neither, Gmail refuses to
>   authenticate and every e-mail fails *silently* — sign-up verification and
>   password resets never arrive.
> * `DEFAULT_FROM_EMAIL` must be an address the SMTP account may send as. Gmail
>   silently rewrites `From:` to the authenticated account unless the alias is
>   verified under Gmail → Settings → Accounts → "Send mail as".

| Variable | Code default | `.env.example` | Notes |
|---|---|---|---|
| `EMAIL_BACKEND` | console backend (prints to the runserver console) | SMTP backend | `django.core.mail.backends.smtp.EmailBackend` for real delivery. |
| `EMAIL_HOST` | `localhost` | `mail.metanoiagroup.co.za` | The domain's own mail server: SMTP 465/SSL. IMAP is 993/SSL for the mail apps; the platform itself only sends. |
| `EMAIL_PORT` | `25` | `465` | |
| `EMAIL_USE_TLS` | `false` | `false` | |
| `EMAIL_USE_SSL` | `false` | `true` | |
| `EMAIL_TIMEOUT` | `20` | `20` | Seconds; auth e-mails send inline, so a slow server must not hang a request. |
| `EMAIL_HOST_USER` | empty | `info@…` | The default connection, used for anything not routed to a sending mailbox. |
| `EMAIL_HOST_PASSWORD` | empty | — | Secret. Spaces are stripped, so an app password pasted as `xxxx xxxx xxxx xxxx` works. |
| `DEFAULT_FROM_EMAIL` | `no-reply@metanoia.local` | `Metanoia Group <info@…>` | |
| `SERVER_EMAIL` | `DEFAULT_FROM_EMAIL` | `info@…` | |
| `EMAIL_FROM_NAME` | `Metanoia Group` | | Display name on the sending mailboxes. |

**Sending mailboxes** (`EMAIL_MAILBOXES`, see `apps/communication/senders.py`).
Each signs in to `EMAIL_HOST` as itself; one with no user sends through the
default connection.

| Mailbox | Variables | Used for |
|---|---|---|
| `accounts@` | `EMAIL_ACCOUNTS_USER`, `EMAIL_ACCOUNTS_PASSWORD` | billing, payments, registration, verification, password resets |
| `info@` | `EMAIL_INFO_USER`, `EMAIL_INFO_PASSWORD` | general information, announcements, notifications |
| `learninghub@` | `EMAIL_LEARNINGHUB_USER`, `EMAIL_LEARNINGHUB_PASSWORD` | new sessions, learning reminders, course notifications |

**Developer accounts** — `DEVELOPER_EMAILS` (comma-separated; the earlier name
`PLATFORM_DEVELOPER_EMAILS` is still read). Default: `dev@metanoiagroup.co.za`,
`seeid24@gmail.com`, `cjmordaunt@gmail.com`. An account whose **verified**
e-mail is on the list becomes a developer and administrator automatically (by
data migration for existing accounts, on confirmation or sign-in for later
ones), and sees the platform tools: error log, audit log, background jobs,
backups and restore. Matched case-insensitively. See `apps.accounts.developers`.

## 7. Metanoia Mail and the seed

Metanoia Mail (`/mail/`, `apps.mailbox`, `docs/METANOIA_MAIL.md`) reads people's
own mailboxes in the hub. These variables seed the mail server settings on first
use; after that the admin's Mail settings page is the source of truth.
`.academic_seed.py` connects a mailbox for each team account whose password is
set: the three sending mailboxes use the `EMAIL_*_PASSWORD` values, the personal
ones `MAILBOX_PASSWORD_*`.

| Variable | `.env.example` | Notes |
|---|---|---|
| `MAILBOX_DOMAIN` | `metanoiagroup.co.za` | |
| `MAILBOX_IMAP_HOST` / `_PORT` / `_SECURITY` | `mail.metanoiagroup.co.za` / `993` / `ssl` | |
| `MAILBOX_SMTP_HOST` / `_PORT` / `_SECURITY` | `mail.metanoiagroup.co.za` / `465` / `ssl` | |
| `MAILBOX_SECRET_KEY` | empty (falls back to `SECRET_KEY`) | Encrypts saved mailbox passwords (`apps/mailbox/crypto.py`). **Set once**: changing it makes every saved mailbox password unreadable. |
| `MAILBOX_PASSWORD_<LOCALPART>` (e.g. `MAILBOX_PASSWORD_DEV`) | empty | Personal mailbox passwords used by the seed, one per personal mailbox. Secrets. |
| `SEED_ACCOUNT_PASSWORD` | empty | First password for any team account the seed has to create (the personal mailboxes, dev@, accounts@, info@, learninghub@). Blank = a random one, printed once. |

`MAILBOX_EMAIL_BACKEND` is the locmem backend under tests and SMTP otherwise.

## 8. Authentication, sign-in and MFA

**Accounts (django-allauth).** The platform is e-mail-only: there is no username
field on any form. Django's `User` still has a required unique `username`
column, which `apps.accounts.adapters.HubAccountAdapter` /
`HubSocialAccountAdapter` keep mirroring the e-mail (allauth would otherwise
derive it from the local part); the custom pages in `apps/myhub/views.py` set
`username = email` directly. `ACCOUNT_SIGNUP_FIELDS` asks only for e-mail and
two passwords; `ACCOUNT_LOGIN_METHODS = {'email'}`; `ACCOUNT_UNIQUE_EMAIL`.
`ACCOUNT_FORMS['reset_password_from_key']` uses `MetanoiaResetPasswordKeyForm`,
which refuses re-setting the current password from a reset link (allauth allows
it by default).

| Variable | Default | Notes |
|---|---|---|
| `ACCOUNT_EMAIL_VERIFICATION` | `mandatory` | `mandatory` (recommended) \| `optional` \| `none`. Mandatory = an account cannot be used until the e-mailed link is clicked (enforced on the custom pages too). Only set `optional` once SMTP is proven to work — otherwise it hides broken e-mail by letting unverified accounts in. |
| `ACCOUNT_EMAIL_SUBJECT_PREFIX` | empty | Subject prefix for allauth e-mails; bodies are in `templates/account/email/`. |
| `ACCOUNT_REAUTHENTICATION_REQUIRED` | `true` | Re-enter the password before adding or removing an MFA factor, so a hijacked session cannot swap in the attacker's own. |

The confirmation link confirms on open (`ACCOUNT_CONFIRM_EMAIL_ON_GET`), does
not log the user in, and lands on the login page whether or not the visitor is
signed in. `LOGIN_URL` and `LOGOUT_REDIRECT_URL` are `/myhub/page-login/`;
`LOGIN_REDIRECT_URL` is `/myhub/`. `SITE_ID = 1`.

**Google sign-in** (`docs/google-oauth-setup.md`)

| Variable | Notes |
|---|---|
| `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_SECRET` | Leave both blank to hide the Google button. Create OAuth 2.0 credentials at the Google Cloud Console with redirect URI `<your-domain>/accounts/google/login/callback/`. |

> Configure Google **either** with these variables **or** as a `SocialApp` row in
> the admin bound to `SITE_ID = 1` — never both. allauth expects exactly one app;
> with both it raises `MultipleObjectsReturned` and every sign-in returns 500.
> `deploy/check_integrations.py` detects this.

Google settings: login starts straight from the button
(`SOCIALACCOUNT_LOGIN_ON_GET`), no extra verification for Google addresses,
scopes `profile email`, PKCE on. `SOCIALACCOUNT_EMAIL_AUTHENTICATION` and
`…_AUTO_CONNECT` let a Google sign-in enter the existing account that owns the
address and record the link — most people register with a password first, and
without these the button sends a confirmation e-mail and leaves them signed out.
This is safe only because Google reports `email_verified` and allauth refuses an
unverified provider address; otherwise it would be an account-takeover route.

**Sign in with Apple** (developer.apple.com → Certificates, IDs & Profiles).
The button stays hidden until all four are set and the key file is readable.

| Variable | Notes |
|---|---|
| `APPLE_SERVICES_ID` | Services ID with "Sign in with Apple". Return URL: `https://<your-domain>/accounts/apple/login/callback/` — Apple accepts only HTTPS on a real domain, never a bare IP or `http://`. |
| `APPLE_TEAM_ID` | Top right of the developer portal. |
| `APPLE_KEY_ID` | Key with "Sign in with Apple". |
| `APPLE_PRIVATE_KEY_PATH` | Path to the downloaded `AuthKey_XXXXXXXXXX.p8`; keep it outside the repository. |

**Multi-factor authentication** (`allauth.mfa`): TOTP authenticator apps plus
10 one-time recovery codes; passkey login off.

| Variable | Default | Notes |
|---|---|---|
| `MFA_TOTP_ISSUER` | `Metanoia Group` | Name shown in the authenticator app. |
| `MFA_REQUIRED_FOR_STAFF` | `false` | `true` makes MFA compulsory for accounts that can change other people's data. |

**Brute-force lockout (django-axes).** Locks on the *combination* of username
and IP, so one attacker cannot lock a legitimate user out from their own
address and a shared NAT address does not lock out a whole office. Resets on
success; the admin shows attempts; lockout page `account/lockout.html`.
Passwords, the POST body and tokens are never written to the attempt log.

| Variable | Default | Notes |
|---|---|---|
| `AXES_FAILURE_LIMIT` | `5` | Matched to allauth's `ACCOUNT_LOGIN_ATTEMPTS_LIMIT` (5). Set higher and axes never fires because allauth's throttle answers first — you keep the audit trail but lose the lockout and its explanation page. |
| `AXES_COOLOFF_MINUTES` | `30` | |
| `AXES_PROXY_COUNT` | `0` (unset) | Number of trusted proxies in front, so the forwarded chain gives the client IP. |

`AUTHENTICATION_BACKENDS`: `AxesStandaloneBackend` **first** (it short-circuits
a locked-out attempt before any password check), then `ModelBackend`,
guardian's object-permission backend and allauth's backend. Password validators
are Django's four standard ones.

## 9. Sessions, HTTPS and CSRF

| Variable | Default | Notes |
|---|---|---|
| `SESSION_COOKIE_SECURE` | `not DEBUG`; on a platform always `not DEBUG` unless the platform sets it | `true` in production. Leave `false` for plain-HTTP local work or the cookie is set but never sent back and logins loop. With `DEBUG` on it is forced off (with a warning) unless `DEV_HTTPS=true`. A false value on a hosted deploy sends the session credential over any plain hop; `deploy.E003` refuses to start. |
| `SESSION_COOKIE_SAMESITE` | `Lax` | `Lax` suits the platform: pages are same-site and the cookie still rides a top-level navigation from an e-mailed link. An empty value means `None`, which widens CSRF exposure and *requires* `Secure` (Chrome drops it otherwise); when Secure is forced off in dev it is reset to `Lax`. |
| `DEV_HTTPS` | `false` | Set when the dev site really is served over TLS, so a Secure session cookie is allowed under `DEBUG`. |
| `LAN_PORTS` | `8000,80,8080` | Ports trusted on this machine's LAN addresses for CSRF. |
| `ALLOW_PLAIN_HTTP` | `false` | For a server with no domain/certificate yet: keeps the site usable over plain HTTP and turns the deploy guards' errors into one loud warning. Remove as soon as HTTPS exists (`switch-to-domain.sh` drops it). |
| `SECURE_SSL_REDIRECT` | `not DEBUG and not TESTING` | Off under tests because the test client speaks plain HTTP and every request would 301. |
| `CSRF_COOKIE_SECURE` | `not DEBUG` | |
| `SECURE_HSTS_SECONDS` | `0` with `DEBUG`, else `31536000` | The AWS host starts at `86400` after the domain switch; raise to `31536000` once everything is confirmed. |
| `SECURE_HSTS_INCLUDE_SUBDOMAINS` | `not DEBUG` | The AWS host sets `false` (`www` and `mail.*` are served by other hosts). |
| `SECURE_HSTS_PRELOAD` | `not DEBUG` | The AWS host sets `false`. |
| `USE_X_FORWARDED_PROTO` | `true` on a platform, else `false` | Sets `SECURE_PROXY_SSL_HEADER`. Turn on **only** when a TLS-terminating proxy (Caddy, nginx, a load balancer) always overwrites `X-Forwarded-Proto`; otherwise a client can claim its request was HTTPS. Leaving it off behind such a proxy with `SECURE_SSL_REDIRECT` is an infinite redirect loop. |
| `CSRF_COOKIE_HTTPONLY` | `false` | Deliberately readable: `theme.js`, the presence ping and the assessment marking page read `csrftoken` from `document.cookie` for `X-CSRFToken`. Turning it on breaks those silently, and it is little defence anyway. Enable once they read the token from a `<meta>` tag. |
| `SECURE_REFERRER_POLICY` | `same-origin` | |
| `PUBLIC_SITE_URL` | `https://metanoiagroup.co.za/` | The public website (the bare domain, hosted separately); the sign-in pages' logo and Home link point here. |

The secure values are what you get by default with `DEBUG=False`; the
variables exist only as overrides, and `apps.diagnostics.deploy_checks` refuses
a `DEBUG=False` build with any of them turned off. They used to be commented out
"for production", which meant production ran without them.

`SESSION_COOKIE_HTTPONLY` is always on. `SECURE_CONTENT_TYPE_NOSNIFF` is on.
`CSRF_FAILURE_VIEW` (`core.csrf.csrf_failure`) sends a stale sign-in or sign-up
form back to a fresh form instead of a bare 403.

**`CSRF_TRUSTED_ORIGINS`** is built once from three sources: the environment
variable (comma-separated, full `scheme://host[:port]`), this machine's LAN
addresses on `LAN_PORTS` (development only — skipped on a platform), and
`https://<RENDER_EXTERNAL_NETLOC>` (behind a proxy Django checks `Origin` on
every unsafe request, so without it every POST, login included, fails with
"Origin checking failed"). It must not be reassigned anywhere else in
`settings.py`.

**LAN access.** To let other devices on the same Wi-Fi reach a dev server, start
it on every interface — `python run_server.py` (prints the LAN URLs) or
`python manage.py runserver 0.0.0.0:8000`. `ALLOWED_HOSTS` is `*` under `DEBUG`
and the LAN origins are trusted as above, so form posts work from the other
device.

| Variable | Default | Notes |
|---|---|---|

**Cache.** With Redis, `IGNORE_EXCEPTIONS` treats an outage as a cache miss:
allauth reads the cache on the sign-up and login path (rate limiting), so a dead
Redis would otherwise turn every auth request into a 500. The swallowed errors
are still logged (`DJANGO_REDIS_LOG_IGNORED_EXCEPTIONS`). Sessions use
`cached_db`, so a Redis restart logs nobody out. Without Redis the cache is
local memory.

**Channel layer.** How a view reaches a connected socket (`config/asgi.py`,
`apps/communication/consumers.py`, `routing.py`, `realtime.py`). In production
it **must** be Redis so every worker shares one bus. The in-memory layer is for
a single-process dev server only — never run more than one process with it, or
each worker gets a disconnected chat bus.

There is no task queue: Celery was removed with the retired CrewAI media
pipeline.

## 23. Logging, Sentry and warnings

**Logging.** Console output goes to the systemd journal on the server
(`journalctl -u metanoia`); the per-person audit trail is the
`ActivityLog` table and faults are in the error log, so there is no log file to
rotate. The `errorlog` handler (`apps/diagnostics/handlers.py`,
`docs/ERROR_CODES.md`) turns every WARNING-and-above record into a catalogued,
deduplicated error-log row, covering the whole codebase rather than only
hand-tagged places. `accounts` and every `apps.*` logger log INFO to both
handlers; `django.request` and `django.security` log WARNING to both.
`django.security.DisallowedHost` goes to the console only at ERROR: a request for
a host we do not serve is a scanner, Django already answers 400, Caddy drops most
of them, and the Django docs recommend exactly this.

**Sentry** — optional, dormant until `SENTRY_DSN` is set. Aggregates unhandled
exceptions across servers with stack trace, request and recurrence.

| Variable | Default | Notes |
|---|---|---|
| `SENTRY_DSN` | empty | |
| `SENTRY_ENVIRONMENT` | `development` with `DEBUG`, else `production` | |
| `SENTRY_RELEASE` | none | |
| `SENTRY_TRACES_SAMPLE_RATE` | `0.05` | Sampled: full tracing on a busy LMS is expensive and rarely more informative. |
